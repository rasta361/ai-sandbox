How the AI Sandbox works

A launcher script on your host starts a throw-away Docker container that runs an AI coding agent (Claude Code, OpenCode/Gemini or Pi) against one project folder. Its only way to the network is a shared Squid proxy with an allowlist. Credentials, history, skills and caches are kept in Docker volumes, so they survive even though the container itself doesn't.

📦 Image = the toolboxEvery tool, wrapper and default config is baked in at build time. Rebuild with --build to update.
🧪 Container = disposableCreated on launch, deleted on exit (compose down). Anything not on a mount disappears.
💾 Volumes = memoryLogins, chat history, skills, plugins, venvs and caches live in named volumes and come back next time.
🔒 Proxy = the only door outThe container sits on an internal network. Its only reachable peer is Squid, which forwards allowlisted domains.

The big picture

These are the moving parts on your machine during a normal (restricted) session, and the paths between them.

Solid green = Docker networks. The sandbox is attached to only ai-sandbox-proxy-net, which has internal: true, so Docker sets up no NAT for it. The proxy is the only container on both networks.

Image vs container

The image is a read-only template built from Dockerfile. A container is one running instance of it. Docker gives the container a thin writable layer on top of the image and plugs in mounts at fixed paths. When the session ends, the launcher runs docker compose down: the container and its writable layer are deleted, and volumes and the image stay.

The “staged config” pattern

Security-relevant configs are not trusted from the volumes, where an agent could have edited them in an earlier session. The image keeps a pristine copy in /opt and the entrypoint re-installs it on every start, overwriting whatever is there:

config/settings.json
(repo)→ COPY → /opt/claude-settings.json
image, 444→ entrypoint cp → ~/.claude/settings.json
in volume, chmod 444
config/opencode.json→ /opt/opencode-settings.json→ ~/.config/opencode/opencode.json
writable layer, 444
config/pi-settings.json→ /opt/pi-settings.json→ ~/.pi/agent/settings.json
in volume, 644 (not a security boundary)

So to change any of these, edit the file in config/ and rebuild. Changes made inside the sandbox are overwritten the next time it starts.

Versions are pinned to the image

CACHEBUST
With --build the launcher passes a fresh timestamp, so the Claude Code layer is re-run and actually fetches the latest version instead of reusing an old cached layer.
DISABLE_AUTOUPDATER=1
Claude Code's in-container updater is turned off. Otherwise it would npm i -g into the persistent volume and the version would drift from one sandbox to the next.
Self-healing purge
The entrypoint deletes @anthropic-ai from ~/.npm-global, because that directory is first on PATH and a stale copy there would shadow the image's claude.

What happens when you run ai-sandbox . --claude

Every step of the launcher and entrypoint in order. The tag on each step says where it runs.

Resolve identity & options host

Takes your UID/GID (or SUDO_UID), loads .env as defaults, then parses flags, which override it: tool, -n NAME, --build, --local-model, --unrestricted.

Inspect Docker state in parallel host

Three background checks: is the proxy running, is a container with this name running, and which of the 6 shared volumes are missing.

Pick a free name host

If ai-sandbox is already running, it picks ai-sandbox-<word> (e.g. -onyx). The name is also the compose project, so each session gets its own container, image tag and per-instance volumes.

Create missing shared volumes host

Runs docker volume create, then a one-off alpine container chowns them to your UID so the non-root agent can write to them.

Ensure the shared proxy proxy

Starts it under its own fixed compose project, ai-sandbox-proxy, if it isn't running. If --local-model is set and the running proxy lacks that rule, it is recreated (a short blip for other sessions). It is skipped entirely with --unrestricted.

Local-model pre-flight (optional) proxy

From inside the proxy it probes host.docker.internal:1234. If that fails, it prints the exact iptables rule, scoped to the egress subnet, and waits for you to retry or skip.

Build if needed, then compose up -d --wait host

If the image tag <name>-sandbox doesn't exist it builds, mostly from the layer cache. --build forces a rebuild with a fresh CACHEBUST. Adds -f docker-compose.unrestricted.yml when --unrestricted is set.

Entrypoint prepares the home container

cd into the project → re-install staged configs → set the git identity and safe.directory → purge any stale Claude Code → point Bun's cache at writable dirs → create ~/.venv_sandbox on first run.

exec the agent container

claude (plus --dangerously-skip-permissions if requested) · opencode . (also used for --gemini) · pi (after writing models.json from LM Studio when --local-model is set). Because of exec, the agent is the container's main process.

docker attach → you're in host

Sets the terminal title to AI SANDBOX (CLAUDE) - "name" @ path and attaches your TTY.

On exit: compose down host

The container and its writable layer are removed. Volumes, the image and the shared proxy are kept for the next session.

Persistent storage: where everything lives

Every path inside the container falls into one of five tiers. Click a tier to filter, and click a row for details.

/home/devuser/<project-basename>/host /path/to/project (rw)bind
Your real project folder. Edits go straight to the host, and git commits made inside land in your host repo. The agent starts here (or in WORKTREE_SUBDIR if set). Project-scoped agent config lives here too and travels with the repo: .claude/settings.local.json, .claude/skills/, CLAUDE.md, AGENTS.md.
~/.claude/volume ai-sandbox-claude-configshared
All of Claude Code's state, shared by every sandbox session at once:
  • .credentials.json, .claude.json: login and account state
  • projects/-home-devuser-<basename>/: session transcripts and auto-memory, keyed by the in-container path
  • skills/: personal skills (e.g. forgejo-token, orchestrating-implementation) and skills/synced/ account-synced skills
  • plugins/: marketplaces, installed plugin versions, installed_plugins.json
  • history.jsonl, file-history/, todos, shell-snapshots, …
  • settings.json: replaced from the image on every start (read-only, 444)
~/.local/share/opencode/volume ai-sandbox-opencode-configshared
OpenCode's auth (Gemini/Google login) and session data.
~/.pi/volume ai-sandbox-pi-configshared
Pi's agent/auth.json and sessions/. agent/settings.json is replaced from the image on each Pi start (writable). agent/models.json is generated when --local-model is set and deleted when it isn't.
~/.config/gh/volume ai-sandbox-gh-configshared
The GitHub CLI token from gh auth login. Every session and agent sees it.
~/go/ · ~/.cache/go-build/volumes ai-sandbox-go-mod-cache, -go-build-cacheshared
GOPATH (module cache plus go install'd binaries, which are on PATH) and the build cache. They are shared on purpose: both are content-addressed and file-locked, so a module is downloaded and compiled once for every project.
~/.npm-global/volume <name>-npm-globalper-instance
npm i -g target (NPM_CONFIG_PREFIX), with its bin early on PATH. The entrypoint purges @anthropic-ai here on every start so the image's Claude Code always wins.
~/.venv_sandbox/volume <name>-python-venvper-instance
A fallback Python venv created on first start. The python/pip wrappers use it when they can't find a project venv, so pip install never touches the system Python.
~/.cache/opencode/volume <name>-opencode-cacheper-instance
OpenCode's cache, including plugins it downloads at runtime such as opencode-gemini-auth.
/tmp/.X11-unixhost X11 socket (ro)bind
Together with DISPLAY, this lets xclip/xsel reach your host clipboard (run xhost +local:docker once on the host). It is a Unix socket, so it works even though there is no network route.
/usr/local/bin/{claude, pi, playwright, go, tofu, …}imageimage
Agent CLIs and toolchains. /opt/opencode, /opt/bun, /opt/ms-playwright (Firefox) and /usr/local/go also live in the image. The only way to update them is a rebuild.
/usr/bin/git · /usr/bin/gh · /usr/local/bin/python3 · pipimage (wrappers)image
Wrapper scripts that sit in front of the real binaries in /opt/real-bin/ and /opt/system-python/. See Security.
/opt/*-settings.json · /opt/pi-localmodel-setup.shimage (staging)image
The pristine copies the entrypoint re-installs on every start. lm-refresh is a symlink to the local-model script.
~/.config/opencode/container writable layerephemeral
This is not a volume. opencode.json and plugin/notification.js are written fresh from /opt on every start and thrown away on exit.
~/.cache/bun · ~/.bun · /tmp · apt installs · everything elsecontainer writable layerephemeral
Anything written outside the mounts above disappears on compose down. To make a tool permanent, add it to the Dockerfile; to make data permanent, add a volume in docker-compose.yml.

Network: fail-closed by topology

The restriction does not depend on programs honouring HTTP_PROXY. A process that ignores the proxy variables or speaks raw TCP/UDP/DNS has nowhere to go, because the network it is on has no route out.

Changing it live

The proxy/ directory is mounted read-only at /etc/squid/allowlist.d. Mounting the directory rather than the file means editor atomic saves are picked up. Edit the file, then run ./ai-sandbox-reload, which sends SIGHUP to Squid. No restart is needed.

Build time is not proxied. Go, OpenTofu, Playwright browsers and the like are fetched freely during docker build.

Local model path (--local-model)

pi in sandbox→ squid (rule 1)→ host.docker.internal:1234→ LM Studio (bound to 0.0.0.0)

At startup pi-localmodel-setup.sh calls /v1/models through the proxy, writes ~/.pi/agent/models.json and makes the first model active. Run !lm-refresh inside pi to rediscover models without restarting. The rule is additive and sticky: once one session enables it, the shared proxy keeps it until ./ai-sandbox --stop-proxy.

How Claude Code skills & plugins are handled

The sandbox has no special code for skills. They live in the Claude volume and in your project, and they persist because those are mounted. There are four sources:

① Personal skills shared volume

~/.claude/skills/<name>/SKILL.md (+ scripts). Available in every project and every session, e.g. forgejo-token, orchestrating-implementation.

② Account-synced skills shared volume

Claude Code writes skills synced from your Claude account to ~/.claude/skills/synced/<bucket>/. They are fetched over the allowlisted .claude.ai / .anthropic.com domains.

③ Plugins from marketplaces shared volume

Marketplaces are GitHub repos cloned into ~/.claude/plugins/marketplaces/ (anthropics/claude-plugins-official, mattpocock/skills). Installed versions go to plugins/cache/<mkt>/<plugin>/<ver>/, tracked in installed_plugins.json with a user, project or local scope. This works because github.com and githubusercontent are allowlisted.

④ Project-level config in your repo

<project>/.claude/settings.local.json turns plugins on for this project (this repo enables mattpocock-skills@mattpocock). <project>/.claude/skills/ and CLAUDE.md work the same way. They live on the host and travel with the repo.

Putting it together, at startup Claude Code sees:
~/.claude/settings.json
image-managed, deny rules+ <project>/.claude/settings*.json
enabledPlugins, project perms+ skills/ · plugins/cache/
skill & plugin files= skills listed in the session
Watch out: because ~/.claude/settings.json is overwritten and made read-only on every start, any user-scope setting you change inside the sandbox (via /config, by enabling a plugin at user scope, or by adding allow rules) won't persist. Put persistent preferences in config/settings.json and rebuild, or in the project's .claude/settings.local.json.

Memory & history are keyed by in-container path

Claude Code keys sessions and auto-memory by working directory, and inside the sandbox that is always /home/devuser/<basename>. So ~/.claude/projects/-home-devuser-ai-sandbox/memory/ belongs to “any project folder named ai-sandbox”. Two host projects with the same folder name share memory and --resume history.

OpenCode & Pi extensions

OpenCode

Plugins are declared in config/opencode.json ("plugin": ["opencode-gemini-auth@latest"]) and downloaded through the proxy (npm/Bun) into ~/.cache/opencode. The local notification.js plugin is copied from the image into ~/.config/opencode/plugin/. Because that directory is ephemeral, any plugin you add by hand inside the sandbox is gone next session.

Pi

Everything Pi keeps under ~/.pi persists (auth, sessions, anything else it stores there), except settings.json, which is reset from the image on each start. The local-model script then writes the active model into it.

Security layers

Defence in depth, strongest layer first. Only the network layer is a hard boundary. The others are guardrails that stop an agent from doing the wrong thing by accident.

1 · Network topology
hard boundary

The container has no route out except Squid, which allows only listed domains on 80/443 and logs every request.

Caveat: broad entries such as .github.com, .google.com and .googleapis.com are still reachable, so data can still leave to those services.

2 · Filesystem scope
hard boundary

Only the project folder, the X11 socket and the named volumes are visible. The agent runs as your non-root UID and there is no Docker socket.

Caveat: the project is mounted read-write, and the volumes holding all your agent and GitHub credentials are mounted into every session.

3 · Agent permission rules
guardrail

Claude's permissions.deny and OpenCode's permission.bash refuse git push, remote edits, gh api/repo/secret/workflow…. The config is re-installed read-only on every start.

Caveat: these match command strings, and --dangerously-skip-permissions removes Claude's prompts. Pi has no such rules.

4 · Command wrappers
guardrail

git blocks push, remote add/set-url/remove and credential. gh is allow-listed: issue *, pr create/view/list/status/diff/checks, auth login/status. The intended flow is that the agent opens a PR and you push from the host.

Caveat: the real binaries are still executable at /opt/real-bin/, so this stops accidents, not a determined process.

Host bridges & helper scripts

🔑 OAuth callback (ai-sandbox-auth)

Browser logins redirect to localhost:8085 on the host, where nothing is listening. You copy that URL, and the script runs docker exec … curl against 127.0.0.1 inside each running sandbox until one answers 200. This replaces port publishing, which the internal network couldn't route anyway.

📋 Clipboard

Through the X11 socket bind mount plus DISPLAY. Run xhost +local:docker on Linux; WSLg works automatically.

🔊 Audio notifications

The OpenCode plugin runs edge-tts → ffmpeg → paplay to PULSE_SERVER=tcp:host.docker.internal:4713. That is raw TCP to the host, so it only works in --unrestricted sessions; in the default topology it fails silently. The terminal bell and title still work.

🖥️ Terminal title

The launcher sets AI SANDBOX (TOOL) - "name" @ path. The OpenCode plugin switches it to ✓ done or ⚠ input needed.

Sharp edges worth knowing

Things that follow from the design and could surprise you. The ones marked “bug” look unintended.

bugProject venvs are never detected

The python/pip wrappers hard-code project_root=/home/devuser/project, but the project is mounted at /home/devuser/<basename>. Unless your folder is literally named project, a repo's .venv is skipped and everything goes to ~/.venv_sandbox.

designUser-scope Claude settings don't stick

~/.claude/settings.json is overwritten and set to 444 on every start. Put persistent settings in config/settings.json (and rebuild) or in project-level settings.

designSame folder name means shared memory

Claude's sessions and memory are keyed by /home/devuser/<basename>, so ~/a/api and ~/b/api look like the same project.

designRandom names leave volumes behind

Each auto-picked ai-sandbox-<word> creates its own npm, venv and OpenCode cache volumes and image tag. They are not cleaned up. Use -n for stable names.

designThe local-model rule is global and sticky

The proxy is shared, so --local-model opens host:1234 for every running session until --stop-proxy.

designAudio needs --unrestricted

PulseAudio is raw TCP to the host and can't go through Squid, so OpenCode's spoken notifications are silent in normal sessions.

designTools are frozen until rebuild

Claude Code, OpenCode, Pi, Go, OpenTofu and Playwright are “latest at build time”. Updating any of them means --build or ai-sandbox-rebuild.

designCredentials are shared everywhere

One gh token and one set of agent logins are mounted into every session, whatever the project. To isolate a project you'd need different volume names.
